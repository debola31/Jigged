# Divergence report — AI Insights & Charts (#336)

Method: compared `docs/modules/ai-insights.md` against the real code paths — `components/insights/*`, `components/dashboard/{PinnedMetrics,InsightsSection,MetricPickerModal}.tsx`, `utils/{insightsAccess,savedInsightsAccess,dashboardAccess}.ts`, the FastAPI `api/routes/insights_routes.py` + `api/tools/{schema_context,sql_validator}.py`, the `saved_insights` / `ai_chat_queries` schema in `supabase/schema.prod.sql`, and the unit/integration tests under `__tests__/` and `api/tests/`.

## Fixed in this PR

- **"17 tables" → "20 tables" (5 occurrences).** The doc said the AI schema context / allowlist covered "17 tables" (Architecture safety layer #3, Chat Flow step 2, the `schema_context.py` Backend-Files comment, and the AI-System-Prompt section twice). The real `ALLOWED_TABLES` frozenset in `api/tools/schema_context.py` contains **20** business tables (the exact list the doc's own "Allowed Tables" prose already enumerates). Changed every "17" to "20".

- **Pinned-metric persistence is Supabase, not localStorage.** The "Pinned Metrics" UI-screen bullet said selection is "Persisted to localStorage per user." It is actually persisted to `user_preferences.preferences.dashboard_pinned_metrics` via `setPinnedMetricKeys()` in `utils/dashboardAccess.ts` (a Supabase upsert keyed on `user_id`), and the time-period toggle to `preferences.dashboard_metric_periods`. Corrected the prose to name `user_preferences`.

- **`GET /api/insights/{company_id}/chat/history` does not exist.** The doc documented a chat-history endpoint (last 20 queries) with a JSON response. `api/routes/insights_routes.py` defines exactly one route — `POST /{company_id}/chat`. Nothing in `api/` serves history (grep for `chat/history` / `history` returns none), and no frontend caller requests it. Removed the endpoint from the "API Endpoints" section.

- **Saved-insights CRUD is client-side Supabase, not FastAPI endpoints.** The "API Endpoints" section listed `POST /saved`, `GET /saved`, `DELETE /saved/{insight_id}` as backend routes. These are implemented entirely client-side in `utils/savedInsightsAccess.ts` (`saveInsight` / `getSavedInsights` / `deleteSavedInsight`) against the RLS-scoped `saved_insights` table — the route file's own module docstring says "Saved insights CRUD … is handled client-side via direct Supabase queries." Replaced those three "endpoints" with a note pointing at the access layer.

- **Stale "insight cache … UNIQUE constraint" validation rule.** Under "Validation Rules," the line "Insight cache is per-company, per-type (UNIQUE constraint)" refers to the dropped `ai_insight_cache` table (the doc's own Data Model section documents its removal). Removed the stale rule.

## Resolved (owner decision)

- **The "max 5 saved insights" cap is dropped — there is no cap.** The doc previously said the "Your Charts" header reads "Your Charts (N/5)", the Save action is "disabled at 5/5 with tooltip 'Remove a chart below to save new ones'", and `saved_insights` is "max 5 per user per company." Reality (confirmed): **no cap** in any layer — `saveInsight()` (`utils/savedInsightsAccess.ts`) inserts unconditionally, `InsightsChat.tsx` has no 5/5 disable or tooltip, `InsightsSection.tsx` renders a plain "Your Charts" header (no count, no `/5`), and `saved_insights` in `schema.prod.sql` carries no unique/check constraint. **Owner decision:** drop the cap from the spec — there is no saved-insight limit. Doc updated: `saved_insights` table note, the Ask-Bar and Your-Charts prose, the ASCII layout, the Phase-0 checklist, and the AC now all state "no cap"; the former "documented-but-not-shipped" AC is rewritten as a positive assertion of the uncapped behavior.

- **`saved_insights` is per-user within a company (not per-company).** Open Question #1 previously resolved to "Per company for MVP," but `getSavedInsights()` and the `saved_insights` RLS policies ("Users can read/insert/delete own saved insights") scope by `user_id = auth.uid()` — each user sees only their own pinned cards. **Owner decision:** per-user-within-company is the intended behavior. Doc updated: Open Question #1 now reads "Per user within a company," the table note and Your-Charts prose call out the `auth.uid()` scoping, and a new AC asserts two users in one company each see only their own cards.

- **No chat-history persistence today; chat is stateless.** The doc previously documented a `GET /api/insights/{company_id}/chat/history` endpoint (removed in an earlier pass). **Owner decision:** confirm there is NO chat-history persistence — each `POST /{company_id}/chat` is an independent Q&A, and `ai_chat_queries` is an analytics/cost log that is not read back as history. `api/routes/insights_routes.py` defines only `POST /{company_id}/chat`. Doc updated: the API-Endpoints prose now states chat is stateless and there is no history route; the Backend-Files comment no longer says "submit + history"; the Phase-1 "multi-turn conversation history" item notes that if added it would be scoped per-user-within-company (mirroring `saved_insights`). *(The RLS policy literally named "Users can read own company chat history" on `ai_chat_queries` governs read access to that log table — it is not a chat-history feature; the security AC's citation of it is accurate and unchanged.)*
