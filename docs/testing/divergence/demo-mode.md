## Fixed in this PR

- **Section 9 "API Endpoints" described `/api/demo/*` FastAPI routes that do not exist.**
  - *What was wrong:* the doc claimed `POST /api/demo/create`, `POST /api/demo/reset`, `GET /api/demo/status`, and `GET|POST|PUT /api/demo/templates` FastAPI routes, and the user flows (§6.1/§6.2/§6.4), Settings section (§7.1), and the frontend nav snippet (§8.2) all called `fetch('/api/demo/create', …)` etc.
  - *What's right:* there are **no** demo FastAPI routes. Grep for `/api/demo` across the codebase returns nothing, and `api/routes/admin_routes.py` only *reads* `is_demo` (to exclude demo companies from the admin company list). The frontend calls Postgres RPCs directly through the typed Supabase client in `utils/demoAccess.ts`: `getDemoStatus` (SELECT on `companies` + reverse lookup), `createDemoCompany` → `supabase.rpc('create_demo_company')`, `resetDemoCompany` → `rpc('reset_demo_company')`, `syncDemoAccess` → `rpc('sync_demo_access')`. This is the repo's Supabase-first architecture (CLAUDE.md).
  - *What changed:* rewrote §9 to document the `utils/demoAccess.ts` functions and the RPCs they call (not HTTP endpoints); replaced the `fetch('/api/demo/create')`/`/api/demo/reset` references in the flows, §7.1, and the §8.2 snippet with the corresponding `demoAccess.ts` calls; noted that status is read client-side via `getDemoStatus`, not `GET /api/demo/status`.

- **Settings route was `/dashboard/[companyId]/settings/demo`.**

  - *What's right:* the demo-mode card is rendered directly on the main settings page `app/dashboard/[companyId]/settings/page.tsx` (`/dashboard/[companyId]/settings`). There is no `settings/demo` subroute — the `settings/` directory contains only `page.tsx`.
  - *What changed:* corrected the route to `/dashboard/[companyId]/settings`.

## Resolved (owner decision)

- **Template content (§3.1 counts + §4.3 `template_data` JSONB schema) described an entity graph the seeder no longer builds.**
  - *Doc said:* §3.1 listed Customers 3, Parts 6, **Operation Types 8**, **Routings 3 (with nodes and edges)**, Quotes 5, Jobs 4, Job Operations 10+, **Inventory Items 8**. §4.3's JSON used `operation_types`, `routings.nodes`/`edges` with `operation_type_ref`, `parts.pricing`, a single `part_ref`/`unit_price`/`total_price` on each quote and job, and an `inventory_items` array.
  - *Reality is:* `seed_demo_data()` (`supabase/schema.prod.sql`) iterates these template arrays: `vendors` (+ `contacts`), `work_centers` (with `kind`, optional `vendor_ref`), `parts` (bought parts with `cost_per_unit` → a NULL-vendor `part_procurement_tiers` row), `parts_bom`, `routings` with a linear `operations` array (each row → `routing_operations` with `work_center_ref`, no edges), `customers`, `quotes` with a `line_items` array (→ `quote_line_items`), and `jobs` with a `parts` array (→ `job_parts`, each optionally carrying `routing_ref` which fans out into job-part operations). It does **not** seed `inventory_items`, and there are no `operation_types`/`nodes`/`edges`/top-level `pricing` concepts.
  - **Decision:** rewrite §3.1 and §4.3 **wholesale** to the current template schema (vendors + work_centers + BOM + linear routing_operations + quote line_items + job_parts; **no** inventory — inventory-in-demo is not a gap to fill). Done: §3.1's stale count table was replaced with an entity-type table grounded in the seeder, and §4.3's JSON was replaced with the real array shape (illustrative one-row-per-array). Counts stay template-dependent because the template row is not committed.

- **Where the active demo template comes from, and why there are no automated tests.**
  - *Doc said:* §10 implied templates are inserted via a seed file / migration (`scripts/seed-demo-template.sql`) or the Supabase SQL Editor, and §11 listed unit/integration/performance tests for `create_demo_company`, `reset_demo_company`, `sync_demo_access`, the company-selector filter, and the operator flow.
  - *Reality is:* no `scripts/seed-demo-template.sql` exists; the only template tooling is `scripts/sync_demo_template.py`, which copies the active row prod → staging. `supabase/seed.sql` inserts no `demo_data_templates` row, so a fresh local/preview stack has **no active template** — `create_demo_company` there **raises** "No active demo template found" (the seeder guards `v_template IS NULL`; it does not seed an empty demo). None of the §11 tests exist (`__tests__/`, `e2e/`, and `api/tests/` contain no demo tests; the sole demo reference is an `is_demo: false` mock inside `companyAccess.test.ts`).
  - **Decision:** the intended direction (**Planned, see #550**) is to source demo-company data from `supabase/seed.sql` — the same graph the tests seed — differing only by company name, and to **delete** `scripts/sync_demo_template.py`. A committed demo seed plus demo-mode tests are an acknowledged gap, **not** yet shipped. Done: §3.1, §4.3, §10, and §11 now document the current state accurately and label the seed.sql-sourced direction "Planned (#550)"; the aspirational §11 test tables are kept but tagged as unblocked-by-#550. No demo tests were added (still a gap), so the §12 ACs remain automation-pending.
