# Divergence report — Inventory (#341)

Method: compared `docs/modules/inventory.md` against the live inventory route (`app/dashboard/[companyId]/inventory/page.tsx`), the part-workspace inventory tab and modals (`components/parts/workspace/tabs/InventoryTab.tsx`, `PartTransactionModal.tsx`, `PartTransactionHistoryTable.tsx`, `PartUnitConversionsEditor.tsx`), the access layer (`utils/partsAccess.ts` stock/transaction functions, `utils/inventoryLocationsAccess.ts`), the schema (`supabase/schema.prod.sql`: `parts`, `parts_unit_conversions`, `inventory_transactions`, `inventory_locations`, `part_location_stock`, `job_materials`, `parts_bom`), and the tests under `__tests__/`.

## Fixed in this PR

- **`inventory_items` / `inventory_unit_conversions` tables no longer exist.** The doc's Data Model documented a standalone `inventory_items` table and an `inventory_unit_conversions` table. The schema comment on `parts` is explicit: *"Unified item master. Replaces the prior two-table split between manufacturable parts and stockable inventory_items."* Stockable items are now `parts` rows with `is_stocked = true`; unit conversions live in `parts_unit_conversions` (comment: *"Replaces inventory_unit_conversions"*). **Changed:** rewrote the Data Model section to document `parts` (stocked subset), `parts_unit_conversions`, `inventory_transactions` (with `part_id`, `item_name`, and the location/discrepancy columns), and to drop the two removed tables.

- **`utils/inventoryAccess.ts` does not exist.** The API-Architecture section said "See `utils/inventoryAccess.ts` for implementation details." There is no such file; stock operations live in `utils/partsAccess.ts` (`addPartStock` / `removePartStock` / `removePartStockGraceful` / `adjustPartStock` / `getPartTransactions` / `updateTransactionNotes`) and location operations in `utils/inventoryLocationsAccess.ts`. **Changed:** repointed the reference to those files.

- **`inventory_transactions.inventory_item_id` was renamed to `part_id`, and the row carries an `item_name` snapshot plus `has_discrepancy` / `location_id` / `location_name` / `transfer_group_id` / `job_operation_id`.** The doc's transaction table listed `inventory_item_id` and omitted these columns. **Changed:** updated the `inventory_transactions` column table to match `supabase/schema.prod.sql`.

- **`routing_materials` → `parts_bom`; job materials snapshot from the part BOM.** The Dependencies and Material-Consumption sections repeatedly named a `routing_materials` table and the function `create_job_operations_from_routing()`. The schema comment on `parts_bom` states: *"Replaces routing_materials — BOM is now part-attached (one BOM per manufactured part), not routing-attached."* The live function is `create_job_part_operations_from_routing(p_job_part_id, p_routing_id)`, which snapshots `parts_bom` rows (`parts_bom_id`, `material_part_id`, `quantity`, `unit`) into `job_materials`. **Changed:** replaced `routing_materials` references with `parts_bom` and corrected the function name.

- **The `/inventory/new`, `/inventory/{id}` and `/inventory/{id}/edit` routes do not exist.** The doc's UI-Screens section described a standalone inventory item Create, Detail, and Edit page under `/dashboard/{companyId}/inventory/...`. In the code, `/inventory` renders only a list of stocked parts; "Add Item" navigates to `/dashboard/{companyId}/parts/new?source=bought&stocked=1&from=inventory`, a row click opens `/dashboard/{companyId}/parts/{id}?from=inventory`, and stock management (current on-hand, Add/Remove/Adjust, unit conversions, transaction history) is the **Inventory tab of the part workspace** (`InventoryTab.tsx`). **Changed:** rewrote UI-Screens to describe the stocked-parts list, the part-workspace Inventory tab, the `PartTransactionModal`, and the location-tracked variant.

- **The Add/Remove/Adjust modal is `PartTransactionModal`, and it is disabled for location-tracked parts.** The doc described a generic "Add/Remove/Adjust Modal." The real component is `components/parts/PartTransactionModal.tsx`; when a part has `is_location_tracked = true`, the tab hides the aggregate buttons and shows `PartLocationInventory` (per-location add/remove/adjust/transfer) instead. **Changed:** named the modal and documented the location-tracked branch.

## Resolved (owner decision)

- **Per-job material consumption tracking → GAP, Planned behind the `inventory_transactions` flag (#550).** _Prior finding:_ the doc's Material-Consumption Flow (steps 3–4), the "Operator Integration" acceptance criteria, and the operator user story described an operator marking each `job_materials` row `consumed` (recording `actual_quantity`) or `skipped`, auto-creating a job-linked `depletion` transaction; in the code that flow does not exist — `job_materials` has only `expected_quantity`/`unit` (no `status`/`actual_quantity`/`consumed_at`/`consumed_by`), no `consumeJobMaterials`/`markMaterialConsumed` function, and `JobPartMaterialsCard` is a **read-only, live BOM-sourced** list (comment: *"Material consumption is no longer tracked per job — the part BOM is the source of truth"*). Depletion today happens only through a deliberate action (part-level `PartTransactionModal` Remove Stock, or the operator `depleteStockAtLocation` graceful flow). **Decision:** this is a **gap to be implemented**, not a removed feature. Per-job consumption tracking is **Planned (see #550)** and must ship **behind the `inventory_transactions` feature flag**. **Doc updated:** Overview lists it under "Planned (behind the `inventory_transactions` feature flag)"; the Material Consumption Flow Note and the read-only-materials acceptance criterion now label per-job consumption Planned (#550) instead of "removed," while continuing to document the manual-depletion workflow that ships today.

- **FR-2 reorder/low-stock → partially delivered; status gating Planned behind the `inventory_transactions` flag (#550).** _Prior finding:_ the Overview listed FR-2 (Reorder Alerts) as "deferred to future phase," but `parts.reorder_point` exists, `deriveStockStatus` computes out/low/in-stock, and the inventory list has a Status filter plus a "Below reorder point" chip — so visual low-stock status ships; only threshold **email notifications** and a dashboard alert list are absent. **Decision:** reclassify FR-2 as **"partially delivered (visual low-stock status only; email/dashboard alerts pending)."** Additionally, the low-stock / reorder-point implementation should sit **behind the `inventory_transactions` feature flag** — reorder-point / low-stock status must **not** render for a company without the flag (gating tracked in #550). **Doc updated:** Overview reclassifies FR-2 as partially delivered and adds the flag-gating requirement; the Inventory-List Status bullet and the part-tab "Below reorder point" chip now carry a Planned (#550) gating note. _Current shipped reality:_ the `inventory_transactions` flag does **not** exist in `lib/featureFlags.ts` yet (only `inventory_locations` and `ai_insights` are registered), so status currently renders unconditionally — the gating is an intended, not-yet-built change captured under #550.

## Decision needed

## Informational / aligned

- The three transaction types (`addition`, `depletion`, `adjustment`) and their meanings match the DB CHECK constraint `inventory_transactions_type_check` and the modal's toggle.
- The unit-conversion model (secondary `from_unit` × `to_primary_factor` → primary unit; live conversion preview in the modal) is intact, just relocated to `parts_unit_conversions`. `convertToBaseUnit` in `lib/unitPresets.ts` performs the conversion.
- Quantity validation rules hold: `parts_quantity_non_negative` and `inventory_transactions_quantity_positive` CHECK constraints enforce non-negative on-hand and positive transaction amounts; `removePartStock` rejects an overdraw, `removePartStockGraceful` clamps to zero and flags `has_discrepancy`.
- Archive (soft-delete), not hard delete: `parts` now carries a `deleted_at` column and "Delete" calls the `archive_parts` RPC (stamps `deleted_at`, never blocks) instead of a SQL `DELETE` — shipped in PR #580. The row is kept and hidden (list/search/picker reads filter `deleted_at IS NULL`), so `parts_unit_conversions` and `inventory_transactions` are **kept** (nothing cascades); the ledger's `item_name` snapshot is still preserved and the `part_id` FK normally still resolves the archived part. See `docs/architecture.md` §16. (`inventory.md` updated to match.)
- Transaction history (date, type, quantity, unit, linked job/operation, notes, pagination) is delivered by `getPartTransactions` + `PartTransactionHistoryTable`; notes are editable post-hoc via `updateTransactionNotes` (RLS `Users can update inventory_transaction_notes`).
- CSV export of the inventory list is client-side via `ExportCsvButton` on the list page (selection-scoped), matching the doc's "client-side CSV generation."
