# Divergence report — Invitation System (#338)

Method: compared `docs/modules/invitation-system.md` against the shipped implementation — `supabase/functions/team-invites/index.ts`, `app/accept-invite/[invitationId]/page.tsx`, `app/auth/confirm/route.ts`, `app/dashboard/[companyId]/team/page.tsx`, `app/dashboard/[companyId]/team/members/new/page.tsx`, `components/auth/Login.tsx`, `types/team.ts`, the `invitations` table + `accept_invitation` function in `supabase/schema.prod.sql` / `supabase/migrations/20260527151536_baseline.sql`, and `docs/prd.md`.

The original headline finding was that sections 4–14 described an un-shipped **FastAPI + token + referral** design that diverged from the shipped feature in almost every structural detail, and about half the spec (the entire referral system) was never built. **The owner has since ruled on every open item** (see Resolved below), and the module doc has been rewritten to describe the shipped implementation as canonical. This report now records those resolutions plus the still-aligned informational notes; nothing about this module remains blocked on a product decision.

## Fixed / rewritten in this PR

- **`accept_invitation()` signature + no token column.** Doc (§6) declared `accept_invitation(p_token VARCHAR, p_user_id UUID)` looking the row up by `token`. Reality: `accept_invitation(p_invitation_id UUID, p_user_id UUID)` looks up by `id`; the `invitations` table has **no `token` column** (columns per `supabase/schema.prod.sql`: `id, company_id, email, role, status, invited_by, accepted_by, expires_at, created_at, accepted_at`). The stale prototype SQL was removed and replaced with the real definition from the baseline migration (inserts `user_company_access(..., name='')`).
- **Sections 3–14 rewritten to as-built.** The token/referral/FastAPI/`/settings/*` prose was replaced with the shipped Edge Function backend (§11), the `/auth/confirm` → `/accept-invite/[invitationId]` accept flow (§9), the `/dashboard/[companyId]/team` tabbed grid + `members/new` invite page (§12), lazy-expire-on-list expiration (§10), and the 3-role model (§1, §3.3).
- **Acceptance Criteria (§16).** Preserved the Given/When/Then bullets and their `*verified by / manual / automation-pending*` clauses; updated the scope note to record the owner decisions and reframed the referral bullet as "descoped (owner decision)".

## Resolved (owner decision)

- **Referral system — descoped.** The earlier §§2–6, §9 (Mode 3), §11.2, §12, §14 referral links, `referral_redemptions`, `redeem_referral()`, `validate_referral_code()`, referral emails, `/settings/referrals` page, and `?ref=CODE` signup do not exist in code, schema, or migrations. **Decision: referrals are out of scope and not on the roadmap.** The referral prose was removed from the doc (reduced to explicit "descoped" notes); the "referral system" AC bullet asserts absence as the expected state.
- **Referral-chain analytics — descoped.** Open Question #2 / the §4.3 note previously claimed "resolved — yes, via `referred_by_company_id`," but that column/table never existed. **Decision: accept as descoped** with the referral system. Open Question #2 now reads "Descoped."
- **Backend runtime — Edge Function is canonical.** The draft (§7, §8, §11) placed invitation logic in FastAPI (`api/routes/invitation_routes.py`, `api/services/email.py`, Python Resend SDK). Reality: the Supabase **Edge Function** `supabase/functions/team-invites/index.ts` owns it, calling Resend over `fetch`. **Decision: canonicalize the Edge Function; Jigged severely limits FastAPI.** §11 rewritten to document the Edge Function routes + `verifyAdmin`; §7 points email at the Edge Function. (`api/services/email.py` remains for other mail but is explicitly noted as *not* wired to invitations.)
- **Accept/signup flow — shipped flow is canonical.** The draft §9 specified a reworked `/signup` with three modes and localStorage token persistence across email-verify → login. Reality: a dedicated `/accept-invite/[invitationId]` page reached via a first-party `/auth/confirm` link; the session is established from hash-fragment/PKCE tokens (`verifyOtp` / `setSession` / `exchangeCodeForSession`), **not** localStorage; `/signup` was never reworked. **Decision: re-document the shipped accept-invite flow as canonical and retire the §9 signup-rework design.** §9 rewritten accordingly.
- **Rate limiting — deferred.** The draft §8 specified DB-backed limits (10 invites/hr, 3 referral links/hr) with a composite `(company_id, created_at)` index; the `team-invites` Edge Function implements none and no such index exists. **Decision: deferred (not shipped).** §8 retitled "Rate Limiting (Deferred)"; §3.2 notes duplicate-pending suppression is the only current write-side guard.
- **`owner` role — removed.** The draft role table (§3.3) and auth pattern (§11.3) allowed both `owner` and `admin`; PRD §79 called the first creator "an Admin (owner)." Reality: `user_company_access_role_check` and `invitations_role_check` are both `admin | user | operator` (no `owner`), and `verifyAdmin` checks `role IN ('admin')` only. **Decision: the `owner` role has been removed; only `admin | user | operator` exist and the inviter scope is `admin`.** All `owner` references in the doc were converted to explicit "no `owner` role" statements.

## Informational / aligned

- **`invitations` table core shape aligns** on the columns that do exist, plus the `idx_invitations_company_id`, `idx_invitations_email`, and partial-unique `idx_invitations_pending_email_company` indexes, and the role/status CHECK constraints (`admin|user|operator` / `pending|accepted|expired|revoked`). Divergence from the draft: no `token` column and therefore no `idx_invitations_token` (now reflected in the doc).
- **RLS policies differ in name/shape but match intent.** The draft showed one `"Company admins can manage invitations"` FOR ALL policy. Reality (baseline): `"Admins can manage invitations"` (FOR ALL via `is_company_admin`) **plus** an extra `"Users can read invitations for their email"` SELECT policy — a superset, noted for completeness.
- **7-day expiry + lazy expiration are as specified** (§3.2, §10): the Edge Function sets `expires_at = now + 7 days` on create/resend and lazily flips overdue `pending` rows to `expired` on list; `accept_invitation` and the accept-invite page both re-check `expires_at`.
- **Duplicate-pending handling aligns** (§3.2 "1 pending per email per company"): enforced both by the partial-unique index and by the POST handler revoking any prior pending row before inserting.
- **Demo-independence holds** (§13): no code coupling between invitations and Demo Mode; the accept flow works regardless of demo state, and demo companies are explicitly blocked as invitation targets.
- **Existing team Edge Function coexists** (§1): `supabase/functions/team/index.ts` (direct member creation) and `team-invites` both feed one unified Team grid, as the reconciliation section intends.
- **`returnTo` allow-list confirmed** (§9.4, §14): `components/auth/Login.tsx` `isValidReturnTo` allows `['/dashboard', '/accept-invite']`, so a no-session invitee round-trips through `/login?returnTo=/accept-invite/{id}` back to the accept page.
- **No automated tests exist** for the invitation system in `__tests__/`, `e2e/`, or `api/tests/` — so every AC bullet is `automation-pending` or `manual`. This is itself a gap worth a follow-up given the May 2026 `jobs.status` incident precedent for untested SELECT paths.
- **Team page location** is `/dashboard/[companyId]/team` (a tabbed Admins/Users/Operators grid), not the `/dashboard/[companyId]/settings/team` of the original §12.1 — now reflected throughout the doc; the `/settings/*` tree does not exist.
