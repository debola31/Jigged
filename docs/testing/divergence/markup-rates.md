The `markup_rates` table and the `seed_default_markup_rates()` function both live in the baseline migration (`20260527151536_baseline.sql`), and the seed is inserted per company by an `AFTER INSERT ON companies` trigger (`companies_seed_default_markup_rates`), not by a one-time data migration keyed to a date. Rewrote the sentence to reference the trigger, and added the `is_default=true` note on the Default rate (matches the trigger's `VALUES`).

## Resolved (owner decision)

- **Canonical semantic = live link with edit-cascade.** The owner ruled that the intended, canonical behavior is: markup rates are **live-linked** to parts (applying a rate sets `parts.markup_rate_id` *and* materializes the tiers); **editing** a rate cascades the new breakpoints to every currently-linked part; **deleting** a rate breaks the link (`ON DELETE SET NULL`) but leaves each affected part on its **last-applied markup** (tiers survive, only the link is severed). This matches the runtime exactly — `applyRateToPart` / `applyDefaultRateToPart` / `bulkApplyMarkupRate` all set the FK, `cascadeRateUpdateToParts` propagates edits, and the `BulkApplyMarkupRateDialog` copy ("the parts will stay linked so future rate edits cascade") already agrees. **Doc updated**: the Overview now leads with "applying a rate creates a live link, not a one-time snapshot" and spells out the edit-cascade / delete-keeps-value split; the "snapshot-applied" phrasing and the stale "copied, for re-applying" Part-linkage note were removed; the Behavior section reframes to "edit cascades to linked parts" + "delete breaks the link, keeps the value."

- **Stale code comments are the two `types/markupRates.ts` + `markup_rates` COMMENT artifacts, tracked in #550.** These still carry the original snapshot-only design (`types/markupRates.ts` JSDoc: *"SNAPSHOT semantics … with no link back. Edits to a rate do NOT propagate"*; table COMMENT: *"Applied to parts via snapshot … no link."*) and directly contradict the code. The owner confirmed they should be corrected to the live-cascade semantic; that cleanup is **tracked in issue #550** (Markup Rates section) and is out of scope for this docs-only pass. The module doc now carries a short note pointing at #550 so a reader who hits the stale comments knows the doc is authoritative.

- **Delete confirmation copy ("snapshot semantics mean nothing cascades") coexists with edit-cascade — accurate for delete.** Both the list bulk-delete dialog and the per-rate edit-page delete dialog read "Parts that previously had a deleted rate applied keep their pricing tiers — snapshot semantics mean nothing cascades." Under the live-link canon this is still **correct for the delete path specifically** (FK is `ON DELETE SET NULL`; tiers survive; the link is what's gone). Any product-language tidy-up of the "snapshot semantics" wording in that dialog rides along with the #550 comment cleanup; no doc change was needed here beyond the reframed delete Behavior bullet.
