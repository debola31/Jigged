# Divergence report — Operator View (#342)

Method: compared `docs/modules/operator-view.md` against the operator app (`app/operator/[companyId]/**`), operator components (`components/operator/**`, `components/operations/StationQRCode.tsx`), the access layer (`utils/operatorAccess.ts`, `utils/companyAccess.ts::getPostLoginRoute`), the operator backend (`api/routes/operators_routes.py`), the schema (`supabase/schema.prod.sql` + `supabase/migrations/*`), and the tests under `__tests__/` and `api/tests/`.

## Fixed in this PR

- **Profile screen contents were wrong.** The Screens table said the Profile page shows "Name, email, current station, sign out." *What's right:* `app/operator/[companyId]/profile/page.tsx` renders operator name, email, **company name**, a **Logout** button, and a **Give Feedback** button — it does **not** show the current station (that lives in the header station selector, `app/operator/[companyId]/layout.tsx`), and the doc omitted the Feedback action entirely. *Changed:* rewrote the Profile row to match the actual page and noted where the station indicator really lives.

- **Added the missing `## Acceptance Criteria` section.** The doc had none. Added Given/When/Then bullets grounded in the shipped UI + access layer + schema, each with a verification clause. The single editable state change (operation completion) and the admin-editable entity (operator name) both carry edit→save→reload bullets; note/inventory mutations cite their unit/component tests.

## Resolved (owner decision)

- **`POST /api/operators` targets a table that no longer exists, and nothing calls it → dead code, delete it (#550); `team-invites` Edge Function is the canonical operator-provisioning path.** *Doc said:* under "Admin", "Operator creation uses the backend (`POST /api/operators`) with the Supabase service-role key — the only operator operation that needs the backend." *Reality is:* (1) `api/routes/operators_routes.py` still does `supabase.table("operators").insert(...)/.select(...)` for create/list/get/reset, but there is **no `operators` table** in `supabase/schema.prod.sql` and **no migration creates one** (only `operator_sessions` ever existed in the baseline, and `20260621132129_drop_operator_time_tracking.sql` dropped that) — so those endpoints would fail at runtime against prod. (2) No frontend code references `POST /api/operators` or `createOperator`; the **actual** operator-provisioning path is the admin team page (`/dashboard/{companyId}/team`, Operators tab) sending a magic-link invite via the **`team-invites` Edge Function** (`app/dashboard/[companyId]/team/members/new/page.tsx` → `supabase/functions/team-invites/index.ts`), which creates the `user_company_access` row with `role='operator'` on acceptance. The Supabase-first admin CRUD in `utils/operatorAccess.ts` (`listOperators`/`getOperator`/`updateOperator`/`deleteOperator`) reads/writes `user_company_access`, consistent with the invite flow. **Decision (owner):** canonicalize the **`team-invites` Edge Function** as the operator-provisioning path; the `POST /api/operators` backend (`api/routes/operators_routes.py`) is **dead code slated for deletion, tracked in #550** — it is not to be revived. *Applied:* rewrote the doc's "Admin" paragraph to describe the team-invite flow as the real path, note operator management runs Supabase-first against `user_company_access`, and flag the dead `POST /api/operators` endpoint for deletion (#550). The AC "Admin: operators" bullets already describe the invite flow (the path that actually runs), so the criteria stay truthful.
