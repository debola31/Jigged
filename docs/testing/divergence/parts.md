# Divergence report — Parts (#334)

Method: compared `docs/modules/parts.md` against the real Parts UI (`app/dashboard/[companyId]/parts/**`, `components/parts/**` incl. the `workspace/` tabs), the access layers (`utils/partsAccess.ts`, `utils/partPricingTiersAccess.ts`, `utils/partAttachmentsAccess.ts`), the FastAPI import routes (`api/routes/parts_import_routes.py`), the `parts` / `part_pricing_tiers` / `part_attachments` schema in `supabase/schema.prod.sql`, and the unit + E2E tests under `__tests__/` and `e2e/`.

## Fixed in this PR

- **`part_pricing_tiers` still documented `base_cost_per_unit` and `unit_price` columns.** The doc's Data Model listed both as columns of `part_pricing_tiers`. The schema (`supabase/schema.prod.sql`) has neither — the table is `id, part_id, company_id, sequence, quantity, markup_percent, created_at, updated_at`. Both derived columns were dropped (migration `20260514`, per the code comments in `PartPricing.tsx` and `replaceTiersForPart`); `unit_price` is recomputed live on every read via `getTiersWithComputedPrices` / `calculateTierPricing`. Fixed the table, the "single-direction data flow" prose, and the Tier-cost section to describe markup-only persistence.
- **Wrong column types on `part_pricing_tiers`.** Doc said `quantity` was `Integer` and `markup_percent` was `Decimal(5,2)`. Schema: `quantity numeric` (decimal-capable — the Pricing UI accepts fractional breaks like `0.32`), `markup_percent numeric(10,6)`. Corrected. Also corrected the unique-constraint name to `part_pricing_tiers_unique_seq`.
- **`parts` table Data Model omitted nine columns.** Doc listed only `id, company_id, part_name, description, created_at, updated_at`. Schema adds `source` (`made`|`bought`), `is_stocked`, `primary_unit` (NOT NULL via `parts_requires_unit`), `quantity`, `reorder_point`, `preferred_vendor_id`, `markup_rate_id`, `legacy_id`, `is_location_tracked`. Added them — these drive made-vs-bought, inventory, the markup-rate link, and location tracking, all of which the module now depends on.
- **"Copy pricing from another part" is described as a live feature but does not exist.** There is no copy-tiers action or `copyTiersFromPart`-style function anywhere in `components/parts/` or `utils/`. It was superseded by **markup rates** (`parts.markup_rate_id` → `markup_rates`, `applyRateToPart`, `applyDefaultRateToPart`, and the bulk "Set markup" dialog). Removed the "Copy from another part" claims from the User Stories, the categories-removal note, the Pricing Card section, and the Acceptance Criteria; replaced with the markup-rate behavior that ships.
- **Cost Breakdown and Pricing are one card (`PartPricing`), not two (`PartCostBreakdown` + `PartPricingTiers`).** Neither `PartCostBreakdown` nor `PartPricingTiers` exists as a component. `components/parts/PartPricing.tsx` renders the cost build-up (Run labor / Setup / Materials) as a summary above the markup-tier table in a single card. Rewrote the Part Detail section and Component references accordingly.
- **Cost Breakdown "qty 1 / qty 10 preview rows" and separate Operations/Materials tables do not render.** `PartPricing` shows three summary rows (run labor per unit, one-time setup, materials per unit) plus the tier table — there are no per-op / per-material tables and no `@ qty 1` / `@ qty 10` amortization preview rows in the current component. Removed those claims.
- **Pricing is NOT auto-saved.** The doc said tier edits auto-save on a ~600ms debounce with no Save button. `PartPricing` commits tiers via an explicit **Save pricing** button with an "Unsaved changes" hint (pricing feeds quotes, so it is deliberately not auto-saved). Corrected the Pricing Card prose and AC.
- **Materials are the part BOM (`parts_bom`), not routing materials.** The doc described a "Materials table" of "routing materials" and materials living on the routing. Routing is operations-only now (`PartRoutingPanel` persists via `saveRoutingWithOperations`); materials are the part-level BOM edited by `PartBomPanel` and feed the cost roll-up (`compute_part_cost_at_qty`). The `routing_materials` table no longer exists in the schema. Adjusted the overview and cost-flow wording.
- **Parts List columns / labels were stale.** Doc: a "Table" with "Part Name, Description, Category, Cost" and a "+ New Part" button. Reality (`app/.../parts/page.tsx`): an **AG Grid** with **Part Name** (plus an inline ⚠ incomplete marker), **Description**, **Source** (Made/Bought chip), **Updated** — no Category column (categories were removed) and no Cost column. The create button is labelled **Add Part**; there is also **Import**, a **Source** filter, a **Completeness** filter, and bulk **Set markup** / **Delete** / **Export**. Empty-state copy is "No parts yet. Add your first part — made in-house or bought from a vendor." Updated the Parts List section.
- **The create/edit routes were wrong.** Doc listed `/parts/{id}/edit` and described the detail page as "Read-only … Edit button." There is no `edit` route. Create is `/parts/new` (renders `PartWorkspace` in create mode, then redirects to `/parts/{id}`); the detail page is an editable **maturity-adaptive workspace** whose identity fields auto-save on blur (`updatePart`) — no edit mode, no Edit button. Rewrote the Part Create/Edit and Part Detail sections, including the tab set (Workspace, Inventory [stocked only], Usage, Files, Activity — Activity's slug is `history`).
- **`saveRoutingWithOperationsAndMaterials` renamed.** The prose (and CLAUDE.md-derived phrasing) referenced `saveRoutingWithOperationsAndMaterials`; the function that `PartRoutingPanel` calls is `saveRoutingWithOperations` (materials were split out to the BOM). Corrected where it appeared in the parts doc.

## Resolved (owner decision)

- **New parts auto-apply the default markup rate — this is the intended onboarding behavior.** `createPart` (`utils/partsAccess.ts:815-823`) calls `applyDefaultRateToPart(companyId, data.id)` after the insert, so a new part is created already linked to the company's default markup rate (a starting tier), not with a blank markup the user must type. **Decision:** auto-applying the default rate is intended; the doc now documents it as intended (not a divergence). The AC bullet under "Markup-rate consumption (part side)" describes the current shipped behavior — `applyDefaultRateToPart` is a no-op when the company has no default rate or the default has no breakpoints, and any failure is non-fatal (the part is still created). No lingering "blank by default" prose remains in the doc body.
- **Markup rates are owned by `docs/modules/markup-rates.md`, not embedded in Parts.** Named, company-wide markup rates (`markup_rates` table) can be applied to a part (making its Pricing card read-only and rate-linked), edited centrally, switched back to "Custom", and bulk-applied to many parts from the list ("Set markup (N)"). **Decision:** do NOT embed a full markup-rates subsection in Parts — that module already owns the rate mechanics (including the identical `BulkApplyMarkupRateDialog` AC). Parts keeps only the part-side interactions (auto-apply on create, view rate-linked breakpoints, fork to Custom) and links out for the rest. The embedded bulk-apply AC bullet was removed (markup-rates.md line 125 already covers it), the Pricing-card section gained a pointer note, and the AC group was renamed "Markup-rate consumption (part side)" with a link to `markup-rates.md`.
