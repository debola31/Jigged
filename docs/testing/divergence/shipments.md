## Fixed in this PR

- **Feature flag no longer exists.** Doc said the module ships "behind a per-tenant feature flag (`settings.features.shipments`)" gated by `isShipmentsEnabled(company)`, with a whole "## Feature flag" section. Reality: shipments are **core (always on)** — `lib/featureFlags.ts` explicitly states the flag was removed, there is no `isShipmentsEnabled` helper, and `KNOWN_FEATURES` has no `shipments` key (only `inventory_locations` + `ai_insights`). Changed: the Priority line, the "## Feature flag" heading/body (now "removed — now core"), and dropped the "Feature-gated by `isShipmentsEnabled(company)`" claim from the surface description.

- **Standalone `/dashboard/{companyId}/shipments` list page does not exist.** Doc described an AG Grid list page (columns Packing Slip #, Ship Date, Customer, Jobs, Method, Carrier, Lines, Created By; 300ms search) hydrated by `listShipmentsForCompanyWithJobs`. That page — and the sidebar entry — were **removed** in commit `c233b50` ("refactor(shipments): remove standalone Shipments page + sidebar entry"); there is no `app/dashboard/[companyId]/shipments/` directory. Rewrote the "Pages" section to document the actual surface: the `ShipmentsMenu` toolbar dropdown on the job detail page.

- **`listShipmentsForCompanyWithJobs` does not exist.** Doc referenced it in prose and in the Access Layer table. No such function is in `utils/shipmentsAccess.ts` (only a stale mention in a test-file comment). Removed both references; the list-hydration row is gone.

- **`/dashboard/{companyId}/shipments/new` wizard does not exist.** Doc described a two-step wizard (customer picker via `SearchableSelect`, `?customer=` param, then `ShipmentForm` in customer mode). Removed with the list page (commit `c233b50`). Creation now happens only via `CreateShipmentModal` (a dialog) on the job detail page, running `ShipmentForm` in **`job` mode**. Rewrote the "Create Shipment" section accordingly and documented the still-present-but-**unwired** customer mode.

- **`ShipmentHistoryCard` does not exist.** Doc had a "Job detail — `ShipmentHistoryCard`" section describing a card/table with a `refreshKey` and `initialPreviewShipmentId`. The real component is `components/jobs/ShipmentsMenu.tsx` — a dropdown menu, not a card. Rewrote the section to describe `ShipmentsMenu` (button reads `Shipments (n)`, items open `PackingSlipPreviewDialog`, void lives in the preview not the menu).

- **`voidShipment` is implemented, not a "Phase 3 placeholder; currently throws".** The Access Layer table said it throws. In fact `voidShipment` auth-guards, stamps `voided_at`/`voided_by` idempotently (`.is('voided_at', null)`), and the void trigger reverses the fulfillment cascade; it is wired to the Void button inside `PackingSlipPreviewDialog` and unit-tested (`__tests__/utils/shipmentsAccess.test.ts > 'voidShipment'`). Corrected the table row.

- **`shipments.notes` column does not exist.** Doc's data-model table listed a `notes` row, and the Create-form field list named `notes`. The `shipments` CREATE TABLE has no `notes` column, `ShipmentForm` renders no notes field, and `CreateShipmentPayload` has no `notes`. Removed `notes` from the data-model table and the form field list. (The RPC carries a trailing `p_notes text DEFAULT NULL` param, but it is dead — the INSERT never uses it; noted this on the RPC description.)

- **`resolveAttentionLine` reads the frozen `ship_to_address` snapshot, not `shipping_address.attention_to`.** The Access Layer table said "ATTN: line comes from `shipping_address.attention_to` only." The function actually takes `Pick<ShipmentWithRelations, 'ship_to_address'>` and reads `ship_to_address.attention_to` (the snapshot captured at insert), so the slip's ATTN matches what it was issued with even after the address changes. Corrected the row.

- **Access Layer table completeness.** Added the two real functions the table omitted — `countShipmentsForJob` (counts voided rows too via the direct `shipments.job_id` column; **no longer gates `deleteJob`** — that path now archives and preserves shipment history, see `docs/architecture.md` §16) and `getJobLastShipDate` (wrapper over the `job_last_ship_date` RPC) — and annotated that `listShipmentsForCompany` and `getOpenJobPartsForCustomer` have no live caller today (the latter feeds only the unwired customer mode).

- **Data-model table missing the document-snapshot columns.** Added the frozen `customer_name` / `bill_to_address` / `ship_to_address` columns (populated by the `snapshot_shipment_party` trigger; rendered by the packing-slip PDF) which the table did not list but which drive the PDF's Bill To / Ship To blocks.

- **RPC return shape.** Doc said the RPC "returns `{shipmentId, packingSlipNumber}`." The SQL `RETURN`s only the new shipment `id`; `createShipment` reads the minted `packing_slip_number` back in a second query to assemble the pair. Clarified, and corrected the parameter list (was `p_carrier, p_shipping_method, p_notes, …`; the real signature is `p_company_id, p_customer_id, p_shipping_address_id, p_one_time_address, p_ship_date, p_carrier, p_shipping_method, p_line_items` + the dead `p_notes`).

## Resolved (owner decision)

- **`one_time_address` XOR constraint `shipments_one_address_source` — DESCOPED.** The data-model table said `one_time_address` was XOR-constrained "via `shipments_one_address_source` constraint," and a schema COMMENT on the column repeats it. In fact no such constraint exists in the current DB: the baseline (`20260527151536`) created it, but migration `20260623021524_add_document_address_snapshots.sql` **dropped** it (`DROP CONSTRAINT IF EXISTS shipments_one_address_source`) because the frozen `ship_to_address` snapshot became the source of truth for the rendered address and the XOR would block `ON DELETE SET NULL`. **Owner decision:** descope the XOR — shipments already snapshot `ship_to_address`, so the constraint adds only marginal DB integrity and no user-facing capability. Doc updated: the data-model row now states there is no XOR constraint (and cites the drop migration); `one_time_address` is documented as reserved-but-unused (Phase 3). The stale `schema.prod.sql` / `types/shipment.ts` COMMENT still references the XOR, but that snapshot regenerates from `scripts/export_schema.py` — not a module-doc fix.

- **`ShipmentForm` customer mode — EXCISE (not carrier integration, unreachable).** The component still carries the entire customer-mode branch (cross-job open-lines picker, "Ready to Ship only" switch, part/job/PO search, per-job groups, single-job lock) plus its access function `getOpenJobPartsForCustomer`, but no surface routes to it (`CreateShipmentModal` only ever passes `job` mode). **Owner decision:** it is unreachable and is **not** a carrier integration — excise it; the code excision is tracked in **#550**. Doc updated: the section now states job mode is the only reachable path and labels the dormant branch + `getOpenJobPartsForCustomer` as dead code slated for removal (Planned, see #550), excluded from the module's documented behavior. Also confirmed there is no FedEx/UPS/USPS carrier API anywhere (`api/`, `utils/`, `components/shipments/` have no carrier-API/tracking/label code); `carrier` is a free-text/dropdown label (`CARRIER_OPTIONS = ['UPS','FedEx','USPS']` + "Other") — the doc now states this explicitly so it can't be read as an integration.
